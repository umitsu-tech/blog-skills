# 詳細レビュー基準

## 1. 技術的正確性

### チェックリスト
- [ ] コードスニペットは実際に動作するか
- [ ] バージョン情報は明記されているか
- [ ] 公式ドキュメントと矛盾していないか
- [ ] 非推奨のAPIや手法を使っていないか

### 確認方法
- 最新のドキュメントをWebSearchで確認
- 特に日付が古い情報は要注意
- ライブラリのバージョンによる差異に注意

## 2. 構成・流れ

### 理想的な構成
1. **導入（20%）** - 何を解決するか、誰向けか、前提条件
2. **本文（60%）** - 手順、コード、説明
3. **まとめ（20%）** - 振り返り、次のステップ、参考リンク

### よくある問題
- いきなりコードから始まる
- 前提条件（環境、バージョン）が書かれていない
- まとめがない
- 話が飛躍する

## 3. 読みやすさ

### チェックポイント
- 1文が長すぎない（50文字目安）
- 専門用語に説明がある（初出時）
- 適切な見出しレベル（h2, h3を正しく使う）
- 箇条書きの活用
- 適度な改行・空白

### 文章のトーン
- 「です・ます」調で統一
- 上から目線にならない
- 読者に寄り添う表現

### 表記揺れチェック（重要）
記事全体で以下の表記が統一されているか確認する：

#### 技術用語
- `JavaScript` / `Javascript` / `javascript` → 正式名称で統一
- `GitHub` / `Github` / `github` → 正式名称で統一
- `API` / `Api` / `api` → 文脈に応じて統一
- `TypeScript` / `Typescript` → 正式名称で統一
- `Node.js` / `nodejs` / `NodeJS` → 正式名称で統一
- `React` / `react` / `ReactJS` → 正式名称で統一

#### 日本語表現
- 「〜できます」/「〜出来ます」→ ひらがなで統一
- 「〜ください」/「〜下さい」→ ひらがなで統一
- 「〜ため」/「〜為」→ ひらがなで統一
- 「など」/「等」→ ひらがなで統一
- 「すべて」/「全て」→ どちらかに統一
- 「わかる」/「分かる」→ どちらかに統一
- 「いただく」/「頂く」→ ひらがなで統一

#### 記号・数字
- 全角数字 / 半角数字 → 半角で統一（日本語文中の数値も）
- `・`（中黒）/ `-`（ハイフン）→ 箇条書きは一貫して
- `「」`（鉤括弧）/ `『』`（二重鉤括弧）→ 用途を統一

#### 英語表記
- 半角スペースの有無（`React Component` vs `ReactComponent`）
- キャメルケース / スネークケース / ケバブケース → ライブラリ公式に従う

## 4. Qiita最適化

### コードブロック
- 言語指定を必ずつける（```python など）
- コメント（`//` など）を含むJSONは言語指定を `js` にする（`json` だとQiitaのシンタックスハイライトが壊れる）
- 長いコードは折りたたみ（details/summary）
- ファイル名をコメントで明示

### リンク
- リンクカードとして表示したいURLは単独行に置く（インラインのMarkdownリンクはカードにならない）
- `:::note` の中に単独行で置いたURLは、Qiita ではリンクカードにならない。カードにしたいときは note の外に出す

### 画像・図
- 代替テキストを設定
- 適切なサイズ（横幅800px程度）
- スクリーンショットは最新の状態で

### その他
- 目次が自動生成されることを意識した見出し
- 絵文字は控えめに（見出しに1つ程度）
