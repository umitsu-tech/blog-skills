# 技術ブログのレビュー

投稿前の下書きをレビューします。基準は一般的な「良い文章」ではなく、書き手の文体ルールと過去記事です。個性を奪わずに、書き手の普段の書き方へそろえる方向で提案します。

## 手順

1. 対象の下書き（`$ARGUMENTS`）を Read します。引数が無ければ「レビュー対象のファイルパスを指定してください」と伝えて終わります。
2. 文体ルール `${user_config.style_file}` を、ほかの資料より先に読みます。未設定かファイルが無いときは、[references/my-style.md](references/my-style.md) をひな形に自分の文体ルールを書き、`/plugin configure blog-skills@ryuki-plugins` で登録するよう案内して終わります。
3. 過去記事の候補をスクリプトで出し、レビュー対象とジャンルが近い記事を 2〜3 本 Read します。ジャンルを決めにくいときは「新しい順」の 3 本を読みます。

   ```bash
   sh "${CLAUDE_PLUGIN_ROOT}/skills/review-blog/scripts/pick-references.sh" "${user_config.articles_dir}/published"
   ```

   スクリプトは published/ の下にある 5KB 以上の記事を、ファイル名でトラブルシュート系（しない・できない・表示されない）、実装・手順系（してみた・を作る・する）、解説系（とは・について）に分け、それぞれ新しい順に並べます。
4. [criteria.md](criteria.md) の観点と、文体ルールとの整合を確かめます。良い例・悪い例は [examples.md](examples.md) にあります。
5. 古い情報やバージョンに依存する記述があれば、WebSearch で最新の情報を確かめます。
6. 下の「出力」のとおりに、レポートを書き出してターミナルに要約を出します。
7. 次の 2 つを見つけたら、文体ルールへの追記を 1 行の形で提案します（改善ループ）。ファイルを書き換えるのは、承認をもらってからです。
   - レビュー対象に繰り返し現れるのに、文体ルールに書かれていない表現や構成の癖 … 「残したい個性」の候補
   - レビューのあとの修正対応で、ユーザーが受け入れなかった指摘 … 「改善提案として出さない」リスト（my-style.md ではセクション 8）への追記候補。セッションの終わりに提案します

## 指摘の 2 層

- 機械的な修正（ユーザーが考えなくていいもの）… 誤字脱字、ひらがな化リストの違反などの表記揺れ、ライブラリの公式表記、リンクカードの形式、裏取りできた明らかな事実誤り。「適用して」の一言でまとめて直せる形で出します
- 判断してほしい提案（ユーザーが考えるところ）… 語り口やニュアンス、構成の組み替え、主張の強さ、個性に関わる表現。1 件ずつ理由を添えて出し、押し付けません

## 観点

| 観点 | 見ること |
|---|---|
| 技術的正確性 | 情報が正しく新しいか、コードが動くか、バージョンが書いてあるか |
| 構成・流れ | 文体ルールにある定型の構成（節の並びと締め方）に沿っているか |
| 文体・語り口 | 文体ルールの語尾・一人称・柔らかい表現が一貫しているか |
| 読みやすさ | 1 文の長さ、専門用語の初出時の説明、見出しの粒度 |
| 表記揺れ | 公式表記（Claude Code、GitHub、Node.js、macOS など）、ひらがな化 |
| Qiita のマークアップ | 単独行の URL によるリンクカード、`:::note`、コードブロックの言語指定 |
| 過去記事との整合 | 過去記事と比べて、文体や構成が浮いていないか |

## 指摘しないもの

- Qiita のタグ（投稿時に手で設定するため）
- SEO や話題性を狙った要素（煽るタイトルの提案など）
- 他人の記事との比較。参考にするのは書き手自身の過去記事だけです
- 書き手の個性。自虐のユーモア、取り消し線、「〜のかなと思いました」のような柔らかい締めなど、文体ルールで残すとしている表現（my-style.md ではセクション 8）

## 出力

詳細はレポートのファイルに書き、ターミナルには要点だけを出します。

### 詳細レポート

下書きと同じディレクトリに、拡張子の `.md` を `.review.md` に替えた名前で Write します（`foo.md` のレビューなら `foo.review.md`）。全優先度の指摘、修正のサンプル、参考にした過去記事、総合評価を入れます。

指摘の番号は全件の通し番号にします。機械的な修正が #1〜#3 なら、判断してほしい提案は #4 から続けます。ユーザーが「4 だけ適用して」のように番号だけで採否を伝えられるようにするためです。2 層の分類はそのまま保ちます。

```markdown
# レビューレポート: <元ファイル名>

生成日時: YYYY-MM-DD HH:MM
レビュー対象: <絶対パス>

## 📊 総合評価
⭐⭐⭐⭐☆（4/5）

## 🎯 文体ルール・過去記事との整合性
- 構成: ...
- 文体: ...
- 末尾: ...
- 参考にした過去記事: ...

## ✅ 良い点
- ...

## 🔧 機械的な修正（判断不要 — 「適用して」の一言でまとめて直せます）

| # | 種類 | 問題箇所 | 修正案 |
|---|------|---------|--------|
| 1 | 誤字脱字/表記揺れ/公式表記/リンク形式/事実誤り | 引用 | 修正案 |

## 💭 判断してほしい提案（ニュアンス・構成・語り口）

| # | 観点 | 問題箇所 | 提案 | 理由 | 優先度 |
|---|------|---------|------|------|--------|
| 4 | 語り口 | 引用 | 提案 | なぜそう思うか | 高/中/低 |

（# は 🔧 からの通し番号）

## 🌱 スタイルガイドへの追記候補
（あれば。記事に繰り返し現れる未記載の癖などを 1 行の形で）

## 📝 修正後のサンプル
（必要に応じて。過去記事との照合付き）
```

### ターミナル

高優先度の指摘、件数のサマリ、レポートのパスだけを出します。中・低優先度の指摘はレポートを見てもらいます。

```
📝 レビュー完了: <元ファイル名>

⭐ 総合評価: ⭐⭐⭐⭐☆（4/5）

🔧 機械的な修正: N件（誤字 X / 表記揺れ Y / その他 Z）
   →「適用して」の一言でまとめて直せます（考えなくてOK）

💭 判断してほしい提案のうち高優先度（N件）:
4. [観点] 問題箇所の要約 → 提案の要約（理由）※番号は🔧からの通し
5. ...

🌱 スタイルガイドへの追記候補: あり/なし

📊 件数サマリ: 機械的 N件 / 判断系 高 N件・中 M件・低 L件
📄 詳細レポート: <レポートの絶対パス>

良い点・低優先度の指摘・修正サンプルはレポートを参照してください。
```

高優先度の指摘が 0 件のときは、次のように短くします。

```
📝 レビュー完了: <元ファイル名>
⭐ 総合評価: ⭐⭐⭐⭐⭐（5/5）

🔥 高優先度の指摘なし。

📊 件数サマリ: 機械的 N件 / 判断系 高 0件・中 M件・低 L件
📄 詳細レポート: <レポートの絶対パス>
```

### 優先度

- 高 … 技術的な誤り、読者の誤解を招く問題、文体ルールや過去記事の構成から明らかに外れているもの
- 中 … 構成や読みやすさの改善、表記揺れ
- 低 … 細かい表現の好み、Qiita のマークアップの最適化
